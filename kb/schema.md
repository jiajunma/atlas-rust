# 页面约定

知识引擎已选定 llm-wiki-compiler。生成页使用工具的原生格式，默认位于 wiki/concepts/；用标签和正文区分知识类别，不把下表直接配置成尚未完整支持来源追踪的 typed profile。本页的自定义元数据只用于已有的人工维护笔记及模板，不要求编译器保留这些字段，也不作为工具 schema。来源和数学证据的规则对所有页面均适用。

## 页面类型

| type | 主要内容 |
| --- | --- |
| concept | 定义、假设、符号、数学依据、例子与反例 |
| algorithm | 输入输出、步骤、不变量、终止依据、复杂度和边界 |
| implementation | 某个版本的模块职责、数据表示、调用者和错误策略 |
| comparison | 在兼容性对齐时记录 baseline 与 Rust 的对应、差异和可观察影响 |
| decision | 背景、备选方案、选择理由、后果及确认方式 |

Rust 的演进是主线，不强制每个主题拆成五篇或附带 C++ 比较。围绕独立问题写有内容的页面，避免为每个源文件创建空壳笔记。起始系统页放在 `wiki/systems`；其他页面按主题组织。

## 主题元数据

| 字段 | 含义 |
| --- | --- |
| id | 稳定、唯一的 ASCII 标识；改标题不改变身份 |
| type | 上表中的页面类型 |
| note_status | `draft`、`reviewed`、`needs_refresh` 或 `historical`，仅表示编辑状态 |
| aliases | 可选的中英文别名 |
| source_snapshot | 相对 `kb/` 的来源快照路径；未读取来源的模板使用 null |

关系使用正文中的相对 Markdown 链接，并说明关系含义，例如“本算法使用”“此实现对应”“此证据仅支持”。未来引入图查询工具时再增加明确的关系字段，不依赖隐含的同名匹配。

## 来源与版本

每篇实质性页面必须有来源段落，标明文件、符号或文献章节，以及来源能证明什么。外部源码引用固定 commit，文献记录版本和章节；当前本地源文件使用相对路径加来源快照。未重新读取的上游实现必须标为“依据已有审查记录”，不能冒充本次直接审查。

`sources/snapshots` 保存只追加的阅读快照：Git base、是否包含工作区改动、所读文件的路径与 SHA-256。哈希是身份记录，不是正确性验证，也不能单凭哈希重建未提交文件。任务提交时需将本任务相关来源与 KB 一起纳入审查；不顺手提交其他人的变更。若来源尚未提交，必须保留这个限制。

当前状态页面更新后绑定新快照；旧快照保留。新旧来源冲突时，先说明分歧及适用版本，不自动删除旧结论。

## 数学与性能结论

正文分别标明数学推导、源码观察、历史执行结果、假设和待验证方案。`note_status: reviewed` 不能代替数学验收。

验收以仓库现有数学账本及其独立复核为准。引用时带上 `claim_id`、entry ID、来源版本、case 范围与限制；同时保留 `acceptance` 与 `status` 两个维度。历史失败报告可作为反例来源，不因此成为已验收的修复。性能结论还需说明计时范围、资源、线程配置、完整结果一致性和 before/after 来源。

## 提交前的文档检查

按当前任务 diff 人工核对：受影响主题是否更新、来源是否支持措辞、链接是否仍有目标、推断是否标明、索引是否可导航、日志是否记录了实质变化。不得借更新 KB 重新执行本地数学算例或将 pending 证据升级为已通过。
