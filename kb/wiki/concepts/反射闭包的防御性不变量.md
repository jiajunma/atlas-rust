# 反射闭包的防御性不变量

反射闭包是 `RootSystem` 从 [[BasedRootDatum：带基根数据与构造不变量]] 枚举有限普通根系的过程。其插入操作 `Closure::insert` 通过自配对检查和重复记录一致性检查，维护根、余根及简单根坐标之间的对应关系；源码注释将这两道检查明确称为防御性检查。^[root-system.md:18-24, root-system.md:64-69]

## 闭包的生成过程

枚举先为每个简单根插入正、负两条记录，简单根坐标分别为 $\pm e_i$。随后以广度优先搜索逐条取出记录，对每个简单生成器计算配对系数，通过 `reflect_weight` 与 `reflect_coweight` 生成候选根和余根，并对简单根坐标的相应分量执行 `checked_sub(coefficient)`，将候选记录插入闭包。^[root-system.md:55-62]

最终根序由闭包 `BTreeMap` 的键序决定，与广度优先搜索的发现顺序无关。根、余根和简单根坐标三张表保持索引对齐，因此同一个 [[RootId 与根系索引对齐|RootId]] 同时标识三者。^[root-system.md:18-22, root-system.md:61-62]

## 插入时的不变量与检查顺序

每次插入首先检查候选根与其余根的自配对关系：
\[
\langle \alpha,\alpha^\vee\rangle=2.
\]
此检查先于重复键检查，因此已经出现过的根也必须再次通过自配对验证。^[root-system.md:64-65]

随后检查根坐标是否已存在。若存在，候选余根和简单根坐标必须与已有记录逐字节一致，否则返回 `"coroot agreement"` 不变量错误。重复候选不会增加闭包的根数。^[root-system.md:65-67]

只有新记录才受基数插入限制：当 `seen.len() == max_roots` 时，插入被拒绝，返回 `RootSystemResourceLimit { resource: "roots" }`。这一运行时拒绝路径与枚举前的静态预算检查不同；兼容包装器 `enumerate` 会将该根数资源错误映射为历史接口的 `ResourceLimitExceeded { limit }`。^[root-system.md:50-53, root-system.md:66-74]

## 防御性检查的证据边界

源码注释称，已知公开 datum 构造路径无法触发自配对或重复记录一致性错误。测试通过直接向私有 `Closure` 注入记录覆盖这两种拒绝路径；另有测试检查每个根的 `bracket(id,id)==Ok(2)`，并覆盖运行时基数拒绝。这些是实现层面的测试锚点，来源包不将其表述为根系层的数学验收。^[root-system.md:64-69, root-system.md:114-125]

该来源属于结构性源码阅读，上游对应关系与 HPC 捕获编号仅转录自代码注释，尚未核对上游字节；本次知识维护也未执行 Atlas、Cargo、测试或 benchmark。^[root-system.md:9-14, root-system.md:135-139]
