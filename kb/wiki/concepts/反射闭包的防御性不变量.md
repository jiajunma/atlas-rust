# 反射闭包的防御性不变量

`Closure::insert` 是 `RootSystem` 构造反射闭包时的候选插入操作。它依次检查根与余根的自配对、重复根记录的一致性，以及新增根的基数限制。源码注释将前两项称为防御性检查，并说明已知公开 datum 构造路径无法触发相应不变量错误。^[root-system.md:64-69]

## 闭包生成与记录对齐

枚举从 [[BasedRootDatum：带基根数据与构造不变量|BasedRootDatum]] 出发，为每个简单根插入正、负两条记录，简单根坐标分别为 $\pm e_i$。随后通过 BFS 逐条取出记录，对每个生成器计算 `coefficient = pair(root, coroot_g)`，对简单根坐标第 $g$ 个分量执行 `checked_sub(coefficient)`，并以 `reflect_weight` 和 `reflect_coweight` 生成候选、加入闭包。^[root-system.md:55-62]

最终根序由闭包 `BTreeMap` 的键序决定，按环境坐标字典序升序排列，与 BFS 发现顺序无关。根、余根和简单根坐标三张表保持索引对齐，同一个 [[RootId 与根系索引对齐|RootId]] 同时索引三者。^[root-system.md:18-22, root-system.md:61-62]

## 插入检查顺序

### 自配对检查

每次插入首先要求 $\langle\alpha,\alpha^\vee\rangle=2$。这项检查先于重复键检查，因此即使候选根已经存在，也必须再次验证自配对关系。^[root-system.md:64-65]

### 重复记录一致性检查

若根坐标已经存在，候选余根和简单根坐标必须与已有记录逐字节一致，否则返回 `"coroot agreement"` 不变量错误。通过检查的重复候选不计入新增根数。^[root-system.md:65-67]

### 新记录的基数限制

新增根在 `seen.len() == max_roots` 时被拒绝，返回 `RootSystemResourceLimit { resource: "roots" }`。重复候选不消耗基数额度，但仍须通过前述自配对与一致性检查。^[root-system.md:64-67]

运行时基数拒绝与枚举前的静态预算检查是不同路径。静态检查依次检查格秩、根数、坐标条目和反射步数，全部采用严格 `>` 比较；兼容包装器 `enumerate` 将根数资源错误映射为历史接口的 `ResourceLimitExceeded { limit }`，其他错误原样透传。^[root-system.md:50-56, root-system.md:71-74]

## 测试与证据边界

测试通过直接向私有 `Closure` 注入记录，覆盖自配对与重复记录一致性两种不变量拒绝路径。另有测试检查每个根的 `bracket(id,id)==Ok(2)`，并覆盖静态资源限制、限额边界与运行时基数拒绝。^[root-system.md:64-69, root-system.md:114-120]

这些测试锚点不构成根系层的数学验收。来源包属于结构性源码阅读，上游对应关系与 HPC 捕获编号仅转录自代码注释，未核对上游字节；该次知识维护也未执行 Atlas、Cargo、测试或 benchmark。^[root-system.md:9-14, root-system.md:124-125, root-system.md:135-139]
