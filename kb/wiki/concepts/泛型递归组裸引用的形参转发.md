# 泛型递归组裸引用的形参转发

泛型递归组裸引用的形参转发由 `typed/type_groups.rs` 中的 `forward_formals` 实现：在泛型递归组内，符合条件的裸类型名会被改写为携带所在组全部形参的类型应用。例如，`MathGenericList` 会变为 `MathGenericList<A>`，而不是作为无参构造器调用处理。^[atlas-core-type-groups.md:36-43]

## 触发条件与重写规则

转发要求表达式为 `Named`、`arity ≠ 0`，且名字查表所得编号属于正在定义的局部名集合 `locals`。满足条件时，表达式被重写为 `Applied`，其参数按 `0..arity` 顺序构造为 `Variable { index }`，从而转发所在组的全部形参。^[atlas-core-type-groups.md:38-43]

`forward_formals` 会递归进入 `Row`、`Function`、`Tuple`、`Union` 和 `Applied` 的子表达式；其他叶节点保持不变。因此，转发也可发生在复合类型内部的裸引用上。^[atlas-core-type-groups.md:44-44]

## 验证与解析顺序

这一改写位于递归图构造之前的组内名解析阶段。`resolve_spec` 采用两遍结构：第一遍进行广度优先验证；第二遍 `resolve` 克隆表达式，先执行 `forward_formals`，再执行 `resolve_in`，并将后者的错误种类改写为 `Program`。相关职责划分见 [[递归类型组的名字解析与校验分离]]。^[atlas-core-type-groups.md:9-13, atlas-core-type-groups.md:17-32]

验证阶段将 `Named` 视为 `supplied=0` 的非显式应用，而 `Applied` 表示显式携带参数。正在定义的局部名永不接受显式参数，即使参数数量恰好等于 arity，也会报出 `Type '{name}' being defined cannot be given type arguments`。因此，裸引用经内部转发得到的应用，与用户显式写出的类型应用具有不同的验证路径；详见 [[递归类型组的显式类型实参限制]]。^[atlas-core-type-groups.md:23-32, atlas-core-type-groups.md:38-43]

非局部名字按类型构造器的 arity 检查参数数量；数量不符会报告实际值与期望值，查表失败则报告名字未指向任何类型。这些诊断均属于 `Program` 类。^[atlas-core-type-groups.md:23-30]

## 证据边界

上述行为依据当前工作区 `typed/type_groups.rs` 的结构性阅读，不构成语言或数学验收。验证顺序与诊断措辞的行为权威是 HPC 语料门，泛型递归组的端到端验收属于其独立 HPC 证据链；本来源不重述这些验收结果。^[atlas-core-type-groups.md:9-15, atlas-core-type-groups.md:46-50]
