# 源码预测与原版捕获的证据分离

源码预测与原版捕获的证据分离，是指将源码阅读推导的行为预期、原版程序实际产生的输出，以及修复后的验证结果分别记录。预测用于设计见证，捕获用于建立原版回归基准，修复验收则限定于实际验证的输入与契约。Weyl 身份修复保留旧 discovery catalog 的 `source_predicted_not_captured` 状态，另建 regression catalog，不将预测数组改称 golden。^[weyl-context-identity-and-sharing.md:13-18, weyl-context-identity-and-sharing.md:138-157]

## 源码预测的作用与边界

源码阅读可以揭示需要验证的语义：original Atlas 按完整 `PreRootDatum` 内容弱驻留活对象；`dual()` 仅在目标的 Weyl group 尚未建立时共享 source 的 group，已预热的目标不会被覆盖。Weyl 元素的 `=`、`!=`、`*` 则先检查 group 地址，不兼容时抛出 `Weyl group mismatch`，且检查先于 `no_value` gate。因此，兼容性涉及对象存活期与构造历史，不能仅由 Cartan 矩阵或结构相等推定。^[weyl-context-identity-and-sharing.md:164-187]

这些规则曾导出两种修复前 Rust 风险：cold-target dual 在原版中能够共享 group，Rust 却可能拒绝；prewarmed-target dual 在原版中必须拒绝不兼容操作，Rust 的关系运算却可能返回布尔值。源码推断指出了见证方向；随后 A1 fresh-process capture 才将这些预期转化为限定输入范围内的观察事实。^[weyl-context-identity-and-sharing.md:189-212]

## 原版捕获如何建立 golden

原版捕获 job `3884807` 以 `COMPLETED 0:0` 结束，独立检查绑定完整 raw streams、冻结的原版 binary、source 和输入。捕获确认：两种 cold canonical-dual 历史下，原版 `=` 为 true、`!=` 为 false且乘法成功，修复前 Rust 则返回相反布尔值并拒绝乘法；对于独立预热的不兼容 owner，原版拒绝关系与乘法，而 Rust 错误地产生布尔值，并仅保留原版八条有序诊断中的四条。^[weyl-context-identity-and-sharing.md:140-146]

回归测试据此冻结四个原版 stdout/stderr golden，并在 `session.rs` 中加入两个普通 `#[test]`，比较完整输出与有序 `(ErrorKind, message)`。这些 expected 来自原版完整流，既不使用 Rust 的错误输出，也不通过 `should_panic` 替代输出契约。相关诊断比较见 [[差分诊断的有序错误摘要契约]]。^[weyl-context-identity-and-sharing.md:148-151]

## 预测失准应单独记录

G2 展示了源码预期也可能需要修正。上游逐行确认表明，canonical dual 从转置 Cartan 重新编号；按来源中的构造分析，任何 `adjoint(G2,·)` 都不能构造该 canonical dual。因此，冻结 contract 对 `WG_DUAL_OWNER` 与 `WG_REVERSE_OWNER` 的 true 预测失准，新的捕获前登记预期两个引擎均输出 false；未来捕获应将其归类为预测失准，而非引擎分歧。^[weyl-context-identity-and-sharing.md:75-89]

同样，`adjoint(G2,false)` 无法占用 canonical dual 的 cold-share 槽位，不能充当有效的预热拒绝见证。后续 fixture 需要用显式转置内容预热目标。这属于 [[Canonical dual 的转置根数据与 G2 预热见证]] 的见证设计问题；截至来源的 2026-10-09 更新，G2 payload 已冻结和彩排，但提交暂缓，后续 fixture 仍为 provisional，不能写成已捕获结论。^[weyl-context-identity-and-sharing.md:89-100]

## 区分 harness 失败、回归失败与修复通过

验证基础设施失败不能充当预期的语义失败证据。首个 BEFORE job `3884862` 在 checker 自检中失败，当时 Cargo、Atlas 和两个回归尚未执行，因此不能据此解锁生产修复；仍需独立的 HPC BEFORE，再进行修复与同一回归的 AFTER。^[weyl-context-identity-and-sharing.md:153-157]

AFTER-v4 同样因 harness 过度要求预热 stderr 逐字节一致而失败，两侧差异在 error envelope 排版。v5 将该契约改为有序 error summary 比较，其余输入保持不变。最终 AFTER-v5 job `3900050` 完成：cold_dual 完整字节相等，prewarmed_dual 的 stdout、退出码与有序 error summary 一致。说明结果时必须保留这两种比较契约的区别。^[weyl-context-identity-and-sharing.md:59-69]

来源将此次修复记录为已通过 A1 限定语义验收，并以生产提交 `690c2b92` 落地；验收记录为 `math_weyl_context_core_after_v5_acceptance_2026_10_06.json`，report SHA 摘要为 `3288480d…`。生产树经过与 v5 源码 manifest 的逐字节核验；这一状态不授予缓存、性能、内存、更高 rank 或更广数学 release。相关落地约束见 [[整树验收清单与生产落地一致性]]。^[weyl-context-identity-and-sharing.md:63-74]

## 证据不能越过覆盖范围

A1 的跨 dual 乘法只涉及 $s_0s_0=1$，不能发现生成元重编号错误或错误复合外来 root permutation。现有 rebind 用例仍由 `wc_alias` 保持旧 datum 存活，也不能证明仅靠保存的 WeylElt 即可维持 datum 生命周期。输出一致性同样不能证明 fresh-equal owner 使用独立 coordinate cell；这些问题需要额外 lifetime fixture 与 HPC-only `Weak`／work-count 守卫。^[weyl-context-identity-and-sharing.md:313-318]

性能证据也必须独立解释。v8 的四次数学调用仅耗时 0.00–0.01 秒，345 秒总作业时间主要来自 281.53 秒构建，不能据此计算 Rust/original 加速比。后续须先完成更广语义 gate，再做 one-build work-count 检查及同节点、交替顺序、fresh-process 的 time/CPU/RSS A/B；`59 → 至多 5` 仍只是调用层面的工作量假设。^[weyl-context-identity-and-sharing.md:159-160, weyl-context-identity-and-sharing.md:320-324]
