# 补全标识符的首次使用顺序

补全标识符的首次使用顺序，是 Atlas 会话层在消费 token 时维护的顺序约束。`next_session_token` 通过 `context.note_completion_token` 记录标识符，要求被包含文件与后续命令保留原始的首次使用顺序。记录发生在实际消费时刻，而不是预先切分整个源文件时。^[atlas-core-session.md:44-46]

## 逐命令执行与记录时机

Atlas 的词法分类依赖先前命令留下的状态，因此 `session.rs` 拥有逐命令执行的外层循环，并且不预切分整个源文件。消费时记录标识符的纪律与这一执行方式相配合。^[atlas-core-session.md:9-14, atlas-core-session.md:44-46]

`run_source` 为每个源创建全新的 `TypedContext`，`run_source_with_context` 则支持调用方持有的上下文。循环在换行处调用 `execute_tokens` 处理命令缓冲，在文件结束处执行剩余缓冲并退出；普通 token 进入命令缓冲。^[atlas-core-session.md:29-40]

## 多行命令中的顺序

标识符记录与命令求值分属不同环节。对于 [[多行命令的增量解析]]，换行终止符使 `allow_more` 为真；若 `parse_command_fragment_in` 返回 `Ok(None)`，会话保留命令前缀，不求值、不产生诊断，并继续在同一缓冲上累积输入。标识符的记录时机仍由 token 的消费决定。^[atlas-core-session.md:44-50]

## 文件包含的职责边界

文件包含由 `session_frame.rs` 负责。原始会话循环遇到包含指令时，会产生 Io 诊断 `file inclusion is only available through a session frame`。因此，跨被包含文件与后续命令的首次使用顺序，需要结合 [[会话循环与文件会话帧的职责边界]] 理解；不能把文件包含描述为原始会话循环自身执行的操作。^[atlas-core-session.md:37-39, atlas-core-session.md:44-46]

## 测试与证据边界

该源码快照的回归库包含 5 个以 `completion` 为前缀的测试。来源没有列出这些测试的具体断言，因此这一计数不能证明所有跨文件或多行命令场景均已覆盖。测试名与家族计数仅标识所记录的源码快照。^[atlas-core-session.md:58-68, atlas-core-session.md:78-80]

来源属于结构性阅读记录，本身不声称语言或数学验收。回归测试采用原版背书的 fixture 与逐字节输出比对，其可执行正确性由 HPC 门验证；相关方法可参见 [[原版背书的语言层回归测试]]。^[atlas-core-session.md:9-14, atlas-core-session.md:63-68]
